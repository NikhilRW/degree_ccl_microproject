# Product administration, order status and delivered-purchase reviews

The application is deployed through the existing `IntelliMartBackend` stack.
Administrator activation is a separate operator action for an actual confirmed,
email-verified account; deployment does not enroll all users, modify delivery
status or replace existing catalogue/review records.

The **Orders tab extension is deployed** at the existing `/admin` URL. Deployment
verification confirmed `IntelliMartBackend` is `UPDATE_COMPLETE` and the
`OrdersByEntity` index is `ACTIVE` after backfill. Existing product/review features
remain available. Do not run status updates against live orders as test data.

## Administrator access

`/admin` has a Products tab for product creation (including initial stock), private
product image uploads and price editing, plus an Orders tab for listing actual
orders and changing their status. Signed-out visitors go to `/login?redirect=/admin`;
signed-in non-administrators see access denied. There is no administrative
password, email allowlist, category editor, user manager, payment editor or analytics dashboard.

CDK creates the **Admins** group in the existing Cognito pool. Every admin RPC
checks the opaque server session and calls `AdminListGroupsForUser` against that
pool using the session's verified Cognito sub. This pool uses generated local
usernames/subs with email sign-in. No client-supplied role or email authorizes an
operation. Membership is not cached in the session, so removal is checked on the
next RPC. An already-issued image POST capability remains usable for its five-minute
lifetime; it cannot create a product without a fresh membership check.

The storefront Lambda gets only pool-scoped `cognito-idp:AdminListGroupsForUser`,
not group-write or user-management permission. Product POST signing adds only
`s3:PutObject` for `products/admin/*` to its existing media-read permissions.

### Product and image storage

- Prices are positive whole INR amounts; optional list price defaults to selling
  price and cannot be lower. Initial stock is a nonnegative integer. Categories
  must already exist; their real name is read on the server.
- IDs, slugs, creation time, empty highlights/specifications/tags and initial
  rating/review count are generated by the server. Creating a product writes
  `CATALOG / PRODUCT#<uuid>` and increments the actual category's product count
  in one transaction. Existing records and their metadata are not replaced.
- Each upload uses a server-generated `products/admin/<sub>/<uuid>.<extension>`
  key and a short-lived exact-key, exact-MIME, exact-size S3 POST. JPEG, PNG,
  WebP and AVIF only, 1 byte–5 MiB, at most six images per product. The browser
  posts the policy fields and file directly to private S3 and checks the response.
- A server-created `ADMINUPLOAD#<sub> / <key>` receipt binds type/size and owner.
  Creation validates the key and receipt and HEADs each actual object to confirm
  MIME/length. It consumes the receipts transactionally, so a key cannot be
  forged, taken from customer uploads, or reused in another product. Receipts
  expire after an hour. Unused uploaded objects are not automatically deleted.
- Stored images remain `s3://<configured bucket>/<key>` references; catalogue
  reads sign temporary GET URLs. Expiring URLs are never saved as product images.
- Price editing compares the expected old prices and updates only `data.price`,
  `data.originalPrice` and root `updatedAt`. A conflicting price edit asks the
  operator to reload; stock, reviews and historical order prices are preserved.

## Reviews require an actual delivered order

The product's Reviews tab checks eligibility for the signed-in customer. Only
an **own persisted order**, under `USER#<session sub>`, with matching `data.userId`,
an ordered product/positive quantity and `data.status === "delivered"` qualifies.
Estimated delivery dates are not evidence of receipt. Customers cannot set
delivery status. Only a server-authorized administrator can change it in the
Orders tab; the existing customer cancellation action remains processing-only.

Fulfilment must confirm actual receipt before an administrator selects Delivered
in the Orders tab. This is the normal admin delivery flow after the extension is
deployed. An AWS operator can still use the supplied utility as a restricted
processing/shipped → delivered fallback, from the repository root with actual identifiers:

```powershell
npm.cmd --prefix backend run order:delivered -- --region ap-south-1 --table "IntelliMartBackend-StoreDataF2B12DA8-1I021QDJUI3P8" --user-id "ACTUAL_COGNITO_SUB" --order-id "ACTUAL_PERSISTED_ORDER_ID" --confirm-received
```

Replace both identifier placeholders from the real order; do not run against
invented orders or use this to simulate receipt. The explicit confirmation is
required. The script uses operator AWS credentials, verifies ownership/identity,
and conditionally transitions only processing/shipped to delivered. Already
delivered is idempotent; cancellation cannot be undone. Its root `deliveredAt`
is the time the operator recorded receipt, not an invented carrier delivery time.
Concurrent cancellation wins or causes the conditional update to fail. No public
server function invokes this script.

### Review contract and consistency

- `reviewEligibilityFn(productId)` and `submitReviewFn({productId,rating,title,body})`
  use server-only customer authentication. Ratings are integers 1–5, title
  1–120 characters and body 1–2,000 after trimming. Browser fields for author,
  user ID, verification or order state are rejected/not accepted.
- One review per user/product at `PRODUCT#<id> / REVIEW#USER#<sub>` with a
  conditional insert. Public `data` has a random review ID, session author,
  server timestamp and `verifiedPurchase: true`; customer ID stays in root
  metadata, outside public review data. The existing public GET returns only
  `data`, not the private key or metadata.
- Submission atomically checks the own order's still-delivered state and product
  line, inserts the review, and updates the product rating/count with optimistic
  concurrency. Aggregate conflicts have at most four attempts, each rechecking
  ownership, delivery and duplicates. No duplicate increments on retries.
- Existing/sample reviews remain unchanged and are **not** marked verified.
  Existing `rating * reviewCount` is the legacy aggregate base on the first real
  review; root `ratingTotal` preserves the running sum thereafter rather than
  reconstructing it from rounded averages. This intentionally preserves legacy
  display counts even when they differ from the sample review rows.
- Only `verifiedPurchase === true` receives a Verified purchase label. No purchase
  history is manufactured, and no existing orders are automatically delivered.

All new browser services retain the existing account-generation checks and use
same-origin server functions, the existing CSRF middleware and HttpOnly sessions.

## Orders tab: all four statuses and safe inventory

The supported status values are exactly **processing**, **shipped**, **delivered**
and **cancelled**. Administrators may change from any one to any other. Each row
shows the real order ID, customer delivery name, creation date, total, purchased
items/quantities and their historical unit prices. There is no payment-capture
action and no invented order data.

Every list and update RPC freshly checks the current server-session user's
Cognito **Admins** membership. Status input accepts only a validated owner ID,
order ID, expected old status and new status. The server reads the actual
`USER#<ownerId> / ORDER#<orderId>` record, verifies its entity/identity and uses
the persisted items, not submitted inventory, totals, addresses or payment data.

| Transition | Inventory effect |
| --- | --- |
| Current status → same status | Idempotent no-op; no repeated stock adjustment |
| Processing/shipped/delivered → cancelled | Restore all ordered quantities exactly once |
| Cancelled → processing/shipped/delivered | Reserve all ordered quantities again; refuse the entire transition if any product is missing or has insufficient stock |
| Processing/shipped/delivered → another non-cancelled status | No stock change |

Status and stock changes use one DynamoDB transaction, with at most 25 order
lines plus the order update. Repeated product IDs are combined into one stock
update per product key. The order update condition compares the old status and
the complete order-data snapshot, so racing customer cancellation, operator
delivery or another administrator cannot partially change stock or overwrite a
changed order. There is no automatic retry that could unexpectedly apply a stale
status choice; conflicts refresh the actual list and ask the admin to retry.

Only `data.status` changes within order data. Root `statusUpdatedAt` and
`statusUpdatedBy` record the server time/actor. Entering Delivered records root
`deliveredAt`; if the status is later changed, that timestamp remains a historical
record of when delivery was recorded, **not** current review eligibility. Item
prices, totals, addresses, ownership, created time and payment status are preserved.
Marking Delivered does not capture payment. Valid existing reviews are not erased
if the order later leaves Delivered; new review eligibility/submission still
requires an own order whose actual current status is Delivered.

### Order-only index, pagination and deployment

CDK adds **OrdersByEntity** to the retained `StoreData` table: partition key
`entity`, sort key `sk`, projection INCLUDE `data` (base `pk`/`sk` keys are automatic).
Existing root `entity: "order"` records are backfilled by DynamoDB when the index
is deployed; there is no seed script, order rewrite or data migration job. Session
records have no order entity and their token fields are not projected.

The list operation **queries this index**, never scans the table, and returns
25 orders plus an explicit next-page cursor. Load more continues until all pages
are loaded; the UI states whether more orders remain. Index queries are eventually
consistent. Strong base-table reads of the validated order keys provide current
order data after status updates, while newly created orders may briefly lag index
discovery. Refresh orders retries discovery and reloads all currently visible
pages. Browser responses contain only the summary fields needed by this admin
screen, not session tokens or unnecessary address/contact fields.

The existing table read/write grant is applied after index creation so CDK grants
index query access as well. Deploy the table/index and application together, keep
the stateful construct IDs unchanged, and wait for CloudFormation/index readiness
before using the new tab. The order-creation email stream worker is still filtered
to **INSERT** only; status changes are UPDATE events and do not resend the
creation email. The operator CLI remains available and does not reopen cancelled
orders; only the administrator transaction performs stock-safe reactivation.
